1. Project Overview
This document provides the complete project plan, technical architecture, implementation strategy, and semester-wise timeline for the Final Year Project titled Gesture-Based Biometric Authentication System. The project is built around the topic of Continuous Gesture Classification and spans two academic semesters.
The system replaces traditional passwords and PIN-based authentication with a fluid, continuous hand gesture captured through a standard webcam. The core intelligence of the system uses Dynamic Time Warping (DTW), a mathematical algorithm that compares the temporal flow and spatial trajectory of two gesture sequences, with zero reliance on deep learning or large training datasets.

1.2  Project Abstract
Traditional authentication systems rely on passwords, PINs, or biometrics such as fingerprints and facial recognition. These methods are vulnerable to theft, spoofing, and unauthorized replication. This project proposes a novel biometric authentication approach using continuous hand gesture recognition as a user credential.
The system captures a user's unique hand movement through a webcam using Google MediaPipe, extracts 21 three-dimensional hand landmark coordinates per frame, and uses the Dynamic Time Warping algorithm to mathematically compare a live gesture attempt against a securely stored template. The entire comparison is deterministic, fast, and runs offline — making it ideal for local deployment on standard hardware.
In the second semester, this core engine is wrapped in a production-grade full-stack web application with a React frontend, Flask REST API backend, JWT-based session management, and a MongoDB cloud database — delivering a complete, demo-ready security product.
 
2. Problem Statement & Motivation
2.1  Problem Statement
Existing authentication systems face critical vulnerabilities. Passwords can be stolen, guessed, or leaked. Facial recognition can be spoofed with photographs. Fingerprint scanners require special hardware. None of these methods provide a truly touchless, hardware-free, continuous movement-based authentication mechanism.
The challenge is to design a system where a user's authentication credential is a dynamic, continuous physical gesture — a movement that is unique to an individual in terms of speed, trajectory, and joint angles — and which cannot be replicated simply by knowing the gesture pattern. This is the core problem that this project solves.

5. System Architecture
5.1  High-Level Architecture
The system is structured as a five-layer pipeline. Each layer is independent, testable, and replaceable, ensuring that a failure in one layer does not crash the entire system.

Layer	Component	Technology	Function
L1	Hand Tracking	MediaPipe + OpenCV	Captures 21 hand landmarks (x,y,z) per frame from webcam
L2	Feature Extraction	NumPy + SciPy	Normalizes and resamples landmark time-series into fixed vectors
L3	Classification Engine	DTW (fastdtw)	Compares live gesture against stored template, returns distance score
L4	Backend API	Flask + SocketIO	Handles all REST endpoints and real-time WebSocket communication
L5	Database	MongoDB Atlas	Stores user data, gesture templates, and authentication logs
L6	Frontend UI	React.js	Provides the user-facing web interface for all interactions

5.2  Data Flow — Registration
Step	Action
Step 1	User opens Register page in browser and enters username
Step 2	Browser activates webcam — user performs their secret gesture
Step 3	MediaPipe extracts 21 landmark coordinates from each frame
Step 4	Landmark sequence (gesture template) is sent to Flask via Socket.IO
Step 5	Flask normalizes and serializes the template as a NumPy array
Step 6	Template is stored in MongoDB Atlas linked to the user's account
Step 7	Success confirmation returned to the browser — registration complete

5.3  Data Flow — Authentication
Step	Action
Step 1	User opens Login page and enters their username
Step 2	Browser activates webcam — user performs their gesture again
Step 3	MediaPipe extracts live landmark sequence
Step 4	Live sequence is sent to Flask via Socket.IO
Step 5	Flask retrieves stored template from MongoDB for that user
Step 6	DTW computes distance score between live gesture and stored template
Step 7	If distance <= threshold: JWT token issued — Access Granted
Step 8	If distance > threshold: Request rejected — Access Denied
Step 9	User redirected to Dashboard (on success) or shown error (on failure)

5.4  DTW Algorithm Explained
Dynamic Time Warping (DTW) is a well-established algorithm for measuring similarity between two temporal sequences that may vary in speed or timing. Unlike Euclidean distance, DTW can align sequences that are compressed or stretched in time.
In this system, a gesture is recorded as a time-series T = [(x1,y1,z1), (x2,y2,z2), ..., (xn,yn,zn)]. When a user registers, this template T_stored is saved. At login, a new sequence T_live is captured. DTW computes the optimal alignment between T_stored and T_live and returns a numerical distance D.
Decision Rule
If D <= threshold  =>  GRANT ACCESS (gesture matches the registered template)
If D > threshold   =>  DENY ACCESS (gesture does not match the stored template)

The threshold value is tuned during testing by recording 20 genuine attempts and computing the 90th percentile DTW distance.

8. Risk Management & Failure Prevention
This section covers every known failure mode of this type of project and the exact mitigation strategy for each. Following these rules will ensure the project does not fail at the final demo.

Risk	Likelihood	Impact	Mitigation Strategy
DTW threshold too strict — genuine user rejected	Medium	High	Test 20 genuine attempts, set threshold at 90th percentile DTW distance
Lighting changes affect MediaPipe detection	High	Medium	Demo in consistent room lighting. Have a fallback recorded video for demo.
Webcam not found (VideoCapture fails)	Low	High	Always test cv2.VideoCapture(0) first. Keep a backup USB webcam on demo day.
CORS errors between Flask and React	High	High	Install flask-cors and add CORS(app) on line 1 of app.py from day one.
MongoDB connection drops during demo	Low	High	Use MongoDB Atlas (cloud). It does not go offline. Do not use local MongoDB.
Socket.IO latency causing slow response	Medium	Medium	Use eventlet async mode. Cap frame rate to 15fps for landmark streaming.
MediaPipe not detecting hand	Medium	Medium	Add on-screen message 'Hand not detected'. Use min_detection_confidence=0.6.
React build errors on demo machine	Low	High	Always test npm run build and npm start before demo day. Deploy to Vercel as backup.

Demo Day Golden Rules
Rule 1: Always demo with MongoDB Atlas (cloud), never local MongoDB
Rule 2: Run the gesture registration fresh before the demo — never use old templates
Rule 3: Demo in the same room and lighting conditions you tested in
Rule 4: Have a 60-second recorded screen recording backup ready in case of hardware failure
Rule 5: Test the complete registration + login flow at least 10 times the day before

You are absolutely cleared to proceed with implementation. However, looking at this from a strict system-design and computer vision perspective, there are **three hidden technical pitfalls** in the design that you need to patch during the coding phase to prevent the DTW algorithm from failing.

### 1. The Spatial Scale & Origin Problem (Critical)

The document states that the system captures 21 `(x, y, z)` coordinates per frame and normalizes the sequence to a fixed length.

**The Issue:** Sequence length normalization fixes the *time* dimension, but it ignores the *spatial* dimension. If you register your gesture sitting 2 feet away from the webcam, your hand will produce a specific set of `(x, y)` coordinates. If you try to log in the next day sitting 3 feet away, the hand will appear smaller in the frame, and the raw coordinates will be completely different. DTW will read this as a massive mathematical error and lock you out, even if the gesture shape was perfect.

**The Fix:** Before saving the NumPy array to disk, you must apply **Spatial Normalization**.

1. Choose a root node (like the wrist, landmark 0).
2. Subtract the wrist's `(x, y, z)` from all other 20 landmarks in that frame so the wrist is always at `(0, 0, 0)` regardless of where the hand is on the screen.
3. Calculate the bounding box of the hand and scale all coordinates so the hand size is uniformly 1.0.

### 2. The "Start/Stop" Temporal Window Problem

Module 1 mentions recording a fixed `N` frames (e.g., 90 frames = 3 seconds) for the gesture.

**The Issue:** Humans are not perfectly precise machines. What if you start your gesture at second 1, but the 3-second recording window cuts off the last half-second of your movement? DTW is great at handling *speed* variations, but if the two arrays represent different *chunks* of the movement (one complete gesture vs. one chopped-off gesture), the distance score will explode, leading to a False Rejection.

**The Fix:** Do not rely on a blind 3-second timer. Implement a dynamic trigger in your Python script. For example, the recording only starts when the user holds up a specific static sign (like an open palm or a pinch) and stops when the hand leaves the frame or forms a fist. This guarantees you are capturing the *entire* gesture trajectory from start to finish every time.

### 3. The Socket.IO Bandwidth Trap (Semester 2)

In Semester 2, the plan states that the browser will send frames to Flask via Socket.IO as base64-encoded images , and Flask will run MediaPipe.

**The Issue:** Sending 30 raw, base64-encoded webcam images per second over a WebSocket to a Flask backend will consume massive bandwidth and cause severe latency. If the network lags, the frames arrive out of order, and your continuous time-series data gets corrupted before DTW even sees it.

**The Fix:** Flip the processing layer. Run MediaPipe directly inside the user's browser using JavaScript (MediaPipe offers a very lightweight JS library). Instead of streaming heavy video frames to the backend, the browser extracts the 21 `(x, y, z)` coordinates and sends *only* the lightweight JSON array of numbers to the Flask API. This cuts your data payload by 99% and completely eliminates latency risks for your demo.
